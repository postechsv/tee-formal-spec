TEE Formal Specification

This project is an executable specification, in Maude and Full Maude, of the GlobalPlatform TEE Internal Core API. It models successful calls, error returns, panics, storage conditions, and the state transitions of cryptographic operations. It also models the trusted application (TA) kernel, the trusted OS, and the rich (REE) application that calls into the TEE, so a complete call can be run from the REE side into a TA and back.

The specification is a set of object-oriented modules over one configuration, and its behaviour is given by rewrite rules. Models are run by rewriting and explored with search, which the test suites in tests/ use. Storage is represented by [[class:Storage]] objects, and API calls observe it only through messages. The entry point is [[file:main]], which defines [[mod:TEE-BEHAVIOR]].

Architecture

The system state is a Maude configuration of objects, messages, and K computations. Each TA instance is a [[class:TrustedApp]], a subclass of [[class:App]] (program and running K computation) and of [[class:TAKernel]]. The TAKernel holds the TA status (normal, outOfMemory, or panic, see [[sort:AppStatus]]), the call status api-call, the storage reference, and a counter for fresh identifiers (module [[mod:TA-KERNEL]]).

The main components are these.

  • REE and TEE environments. A [[class:Device]] holds an [[sort:Envs]] value, a pair of configurations {REE}|{TEE}. The rules [[rule:accept-smc-request]] and [[rule:return-smc-request]] of [[mod:EXECUTION-ENV]] move secure monitor call (SMC) messages across that boundary.
  • Rich application. [[class:RichApp]] is the REE client. Its behaviour, in [[mod:RICH-APP-BEHAVIOR]], turns a call to teecInvokeCommand into an SMC request, and assigns the returned values when the response arrives.
  • Trusted OS. [[class:TrustedOS]] is the OS kernel of the TEE. It holds the session map from session identifiers to TA instances, the queues of OS services, and the map from application identifiers to TA programs. It creates a TA instance when a TA asks to open a session with it, and it forwards SMC requests to the TA of their session. Its behaviour is in [[mod:TEE-OS-BEHAVIOR]].
  • Storage. [[class:Storage]] holds the file set of one TA. It answers the storage messages declared in [[mod:TEE-MSG]], such as getStatus, checkFileExist, and notifyFileDeletion. Each TA instance has its own storage object, created with it.
  • Sessions. [[class:Session]] records the request and return of one TA-to-TA session (module [[mod:SESSION-BEHAVIOR]]).
  • Objects and handles. Transient objects ([[class:TransObj]]), persistent objects ([[class:PersistObj]]), enumerators ([[class:EnumeratorObject]]), and crypto operations ([[class:CryptoOp]]) are top-level objects. Handles are top-level objects too, subclasses of [[class:Handle]] such as [[class:ObjHandle]], whose oid names the object they refer to (module [[mod:HANDLE]]).

Life of an API call

The clearest example is TEE_AllocateTransientObject ([[op:AllocateTransientObject]]), which completes in one step. A TA program reaches it through a trusted stub built by [[op:defineSysCall]] (module [[mod:TEE-API-IMP-PROG-AUX]]). The call status ([[sort:CallStatus]]) moves through noCall, init, exec, final, and return. The call itself is a term F[ARGS] of sort [[sort:Call]] (module [[mod:TEE-API-CALL]]): the API name applied to an ordered list of # item arguments ([[sort:ArgList]]). The steps are these.

  1. [[rule:tee-api-call]] (in [[mod:TRUST-APP-IMP-BEHAVIOR]]). A call of the API by a normal TA with no call in progress binds the parameters of the stub, whose signature [[op:getFuncParams]] returns, and runs the stub body. The stub evaluates its inputs, sends them with $in, and waits with $wait.
  2. [[rule:tee-api-call-accept]] (in [[mod:TRUST-APP-IMP-BEHAVIOR]]). When the TA is normal and its call status is noCall, it accepts the $in arguments and sets the status to init(makeCall(...)). For this API, [[op:makeCall]] is defined in [[mod:TRANSIENT-OBJECT-TEE-CALL]]. It gives AllocateTransientObject[# OBJTYPE # KEYSIZE].
  3. [[rule:allocate-transient-success]] (in [[mod:TRANSIENT-OBJECT-BEHAVIOR]]). From init, when the type and size are supported, the call moves directly to return(AllocateTransientObject[# success # oid(N + 1, TK)]): the return code comes first, then the outputs. The counter advances by two. The rule creates a [[class:TransObj]] with identifier oid(N, TK), no attributes, and initialized : false. It creates the handle with [[op:freshTransientHandle]].
  4. [[rule:tee-api-call-return]] (in [[mod:TRUST-APP-IMP-BEHAVIOR]]). When the status is return, the pending $out is replaced by the statement from [[op:makeReturnStmt]]. On success that statement stores the handle in the out parameter and sets ret to success. The call status goes back to noCall.

Two error paths of the same call return without creating an object. [[rule:allocate-transient-out-of-memory-err]] returns errorOutOfMemory when the TA status is outOfMemory. [[rule:allocate-transient-not-supported-err]] returns errorNotSupported when the type or size is not supported. The rule that would set the status to outOfMemory is commented out in [[file:tee-kernel]], so that status is reached only from an initial configuration.

Calls with more than one step use exec, with a step number as the second argument. TEE_OpenPersistentObject enters exec(...,0) when it sends getStatus to the storage, and exec(...,1) after a normal retStatus arrives, when it sends checkFileExist (rule open-persistent-status-normal). It enters final when the file exists, and [[rule:open-persistent-success]] returns the handle.

Calls that involve another TA use the same statuses, with messages to the [[class:TrustedOS]]. [[rule:open-session-subroutine]] sends an openTASession request, [[rule:open-ta-session]] creates the TA instance and its storage, and [[rule:open-session-success]] creates the [[class:Session]] and returns its handle. TEE_InvokeTACommand stores its request in the session object; the rules of [[mod:SESSION-BEHAVIOR]] run the target TA, and [[rule:invoke-ta-command-top-level-return]] sends the result back to the caller.

A TA command invoked from the REE follows these steps.

  1. [[rule:invoke-ta-smc]] creates smcReq from the $in arguments of the RichApp's teecInvokeCommand.
  2. [[rule:accept-smc-request]] moves the request into the TEE configuration.
  3. [[rule:handle-smc-request]] sends invkTa from the TrustedOS to the TA of the session.
  4. [[rule:handle-invoke-ta]] starts the TA program with mkConf and records the requester as client-service.
  5. [[rule:handle-invoke-ta-finish]] returns invkTaRet when the program has finished. [[rule:handle-smc-request-finish]] turns it into smcRet.
  6. [[rule:return-smc-request]] moves the response back to the REE. [[rule:invoke-ta-finish]] assigns the output values.

If the TA is in panic while a request is pending, [[rule:return-smc-request-panic]] returns errorTargetDead to the REE application instead.

Model programs

A TA is a program in a small typed imperative language, defined in [[file:imp]]. It has C-like statements, functions with value and reference parameters, structs, arrays, and labelled goto. Its semantics is a K-style rewriting system over a configuration of cells (k, environment, store, call stack; sort [[sort:KConfig]]).

API functions are reached through trusted stubs declared in [[file:tee-imp]]. Each stub, made by [[op:defineSysCall]], waits for the API status and writes the outputs back. [[op:makeCall]] converts the arguments into the ordered argument list of the call, and [[op:makeReturnStmt]] converts the returned list back into statements. A TA program P starts with the syscalls prefix of [[mod:TEE-API-IMP-PROGRAM]] and runs as mkConf(syscalls P, FID, VL), where FID is the command. [[file:app]] builds the configuration only for a well-typed program; otherwise the result is illTyped.

Errors and panics

Errors defined by the API are return codes: a failing call returns F[# RC], for example errorOutOfMemory, errorNotSupported, or errorItemNotFound. Storage failures are mapped to return codes by storageErrCode in [[mod:TEE-OS-BEHAVIOR]].

Programmer errors are panics, which set the TA status to panic. [[mod:GENERAL-PANIC]] covers null handles: [[op:nullHandlePanics]] lists the APIs for which the null handle is an error, and [[rule:null-handle-panic]] applies it. Access rules live in the feature group files, for example [[rule:delete-access-panic]] in [[mod:PERSISTENT-PANIC]] and [[rule:read-access-panic]] in [[mod:DATA-STREAM-PANIC]].

Feature groups

The feature table is in mk/features.mk. Each feature in the table below drops its files from the build when it is set to 0.

FeatureFilesNotes
TRANSIENT[[file:transient]]Transient object API. The shared module [[file:transient-object]] is always loaded.
PERSISTENT[[file:persistent]], [[file:persistent-panic]]Persistent object API and storage errors. The shared module [[file:persistent-object]] is always loaded.
GENERIC[[file:generic]]Generic object API, for either kind of object.
DATA_STREAM[[file:data-stream]], [[file:data-stream-panic]]Persistent data stream access. Requires PERSISTENT.
ENUMERATOR[[file:enumerator]]Persistent object enumeration. Requires PERSISTENT.
CRYPTO[[file:cryptographic]], [[file:crypto-panic]]Cryptographic operation APIs. Keys are transient objects, so this requires TRANSIENT.

All other files, including the client, OS, handle, and IMP files, are always loaded. The protected persistent object behaviour and the TA termination rules are commented out in the current sources.

Reading guide

Read these files in this order.

  1. README.md, then [[file:main]], for the list of modules that make up the model.
  2. [[file:tee-kernel]] and [[file:tee-api-call]], for the TA kernel and the call status.
  3. [[file:tee-app]] and [[file:ree-app]], for the TA and the REE client, and the invocation rules.
  4. [[file:os]] and [[file:os-service]], for the environments, the TrustedOS, and the storage messages.
  5. [[file:handle]], for handles and their creation.
  6. [[file:transient]], then [[file:tee-imp]], for one complete API group and the stubs that call it.
  7. [[file:tee-client]] and [[file:tee-panic]], for the client API and the general panics.
  8. [[file:imp]], for the program language, and [[file:app]], for how a program is started.

The generated index pages list every module, sort, class, operator, and rule: modules.html, sorts.html, ops.html, and rules.html.

The module map at the top of modules.html lists every module by feature (rows) and kind (columns). Each module heading on a file page links to its kind on that page and has a Related modules panel.
